# Adaptive Fitness Coach

## Mission

A mobile-first strength-training and physique-management platform. It must work
exceptionally well for one individual user now, while remaining structurally
ready for trainers, coaches, gyms, and sports professionals later.

The product's distinguishing feature is a **deterministic coaching engine**: the
decision to add weight, hold, or back off is computed from recorded training
data by testable rules, not generated by a language model. Generative AI is out
of scope until the deterministic engine has passed its acceptance criteria.

## Users

- **Now:** one individual training for lean muscle gain and strength.
- **Later:** trainers and coaches managing clients; gyms and sports teams.

Nothing in the schema should make that later step a rewrite, and nothing should
be built for it before a real requirement arrives.

## Architecture

One deployable. Laravel application, PostgreSQL on Supabase, private
S3-compatible object storage for progress photos.

```text
HTTP route → Form Request → Controller → Policy → Application service
          → Domain service (pure) → Eloquent model → PostgreSQL
```

The rule that matters most: **the coaching engine is pure PHP with no Eloquent
dependency**. Its services accept plain data and return plain results.
Persistence, transactions, and HTTP live outside them. This is what keeps the
rule suite fast enough to be worth running.

See `docs/architecture.md` for the current state and `docs/decisions/` for why
it diverges from the YSM scaffold.

## Domain terminology

| Term | Meaning |
| --- | --- |
| Prescription | What a program asks for: sets, rep range, target RIR, rest |
| Snapshot | The prescription copied into a workout when it starts; never edited afterwards |
| Working set | A set that counts toward adherence and session volume; warm-up, drop, and failure sets do not |
| Backoff set | A lighter set after the main work; counts toward session volume |
| RIR | Reps in reserve — how many more reps could have been done |
| E1RM | Estimated one-rep max, Epley: `weight × (1 + reps / 30)` |
| Comparable session | A past session of the same exercise close enough in prescription to compare against |
| Target | The prescription the coach recommends next time, scoped to user + template + template exercise + exercise |
| Coaching state | Whether a target is normal, pain-held, recovery-held, or lacking data — separate from its lifecycle |
| Training Analysis | The user-facing name for the engine's output. Never call it "AI Analysis" |

## Database conventions

- Ownership column is `user_id`, indexed, with a foreign key. Not `tenant_id` —
  see `docs/decisions/ADR-0002-user-id-ownership.md`.
- Body weights are stored in **kilograms** and heights in **centimetres**,
  always. Unit preference is display only.
- Important invariants are enforced at the database boundary as well as in Form
  Requests: unique keys, foreign keys, and check constraints.
- Migrations are additive. **Never edit a migration that may already have run.**
- Laravel migrations are the source of truth. `supabase/` mirrors the SQL as
  actually applied — see `docs/database.md`.

## Authentication and authorization

- Laravel Sanctum. A first-party same-site client gets a session cookie; a
  native client names its device and receives a bearer token.
- **Authorization is enforced in Laravel policies**, one per user-owned model.
- **Ownership is always derived from the authenticated session.** A `user_id`
  in a request payload is stripped and ignored. There is a test for this.
- Row Level Security is not the authorization boundary here, but every table
  has RLS enabled with no policies so that Supabase's PostgREST endpoint
  cannot reach application data. See `docs/decisions/ADR-0001-laravel-authorization.md`.

## Deterministic coaching rules

The full specification lives in `docs/deterministic-coaching-engine.md`. The
rules that are most often got wrong, stated here so they are hard to miss:

1. **Missing RIR blocks a load increase** on the strength of one workout.
   Prefer maintain, or rep progression, with reduced confidence.
2. **Mixed loads are not all main sets.** `70×10, 70×10, 65×10` is two
   successful sets at 70, not three.
3. **One poor workout never reduces load** and never confirms a decline.
4. **Low readiness alone never holds progression.** Low sleep with excellent
   performance is caution and lower confidence, not a hold.
5. **Pain is scoped to the exercise where it was reported.** Knee pain does not
   hold biceps curls. General session pain is caution, not a blanket hold.
6. **Assisted movements reduce assistance**, they do not increase weight.
7. **Bodyweight movements track reps** and never have their range changed
   automatically.
8. **`insufficient_data` never replaces a valid active target.**
9. Every result carries `engine_version`. A rule change means a **new version**,
   never a silent reinterpretation of stored history.

## Future AI boundaries

When generative AI is eventually added, the flow is fixed:

```text
validated workout data → deterministic engine → structured context
→ AI explanation → validated proposal → user approval → application service
```

Only four interfaces are planned, and they are documented in
`docs/product-roadmap.md` as signatures only: `buildWorkoutCoachContext()`,
`buildWeeklyCoachContext()`, `proposeWorkoutAdjustment()`,
`proposeExerciseSubstitution()`.

**AI must never execute SQL or mutate workout records directly.** It explains
and proposes; the deterministic engine and the user decide.

## Prohibited shortcuts

- Do not put coaching logic in React components. The backend is authoritative.
- Do not mutate a workout snapshot after the session has started.
- Do not skip, disable, or loosen a test to get a green run.
- Do not claim a test, build, migration, or deployment passed without running it.
- Do not trust a client-supplied ownership identifier, ever.
- Do not add nutrition tracking. It is documented future scope.
- Do not run the constraint or concurrency suites on SQLite and call them passed.
